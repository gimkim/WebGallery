- Continuous-feed optimization: one bounded64-row page prefetched ahead; exclusion snapshot includes entire current page and in-flight identities to prevent duplicate dispatch. Up to2x background-worker preparation/finalization tasks feed unchanged bounded local/remote generation queues (max32 preparation tasks). Generation counts are not increased. Medium small-eligibility checks share250ms cache invalidated by normal index changes, reducing repeated full-index probes; medium page queries remain live. No mandatory inter-page sleep; drained feed/error polling unchanged.

- Retry-aware scheduling: HasRunnableSmall, not total pending small, gates medium background. PendingMedium excludes only small work whose retry deadline has arrived, and selects only sources with small ready. Failed/deferred small images do not block idle-time medium work; deadline expiry restores small-first ordering. This supersedes the earlier all-small-including-deferred restriction without altering on-demand preemption.

- Failure retry now30 seconds. Background immediately reconciles parent metadata on failed generation or stale/missing source validation; deleted files leave the index, changed sources reset their readiness/retry, inaccessible roots preserve the last snapshot. Existing one-hour retry deadlines are shortened on startup upgrade. Preemption remains separate and does not use failure retry.

- Latest thumbnail policy supersedes the previous remote-only medium and static Management snapshot decisions. Small/medium use remote-first/local fallback. Queues order on-demand small, on-demand medium, background small, background medium; active background is cooperatively cancelled and paused across either foreground execution host, not marked failed/offline. Background medium requires no incomplete small fingerprints anywhere in the current index (even deferred small errors block it). New small discoveries stop further medium feed. Medium readiness/retry are separately persisted, indexed refresh invalidates both sizes, and cache keys do not change. Configured worker caps/disabled background remain respected.
- Management small/medium progress uses a single joined owner aggregate, shared10-second result cache and query gate. One page-scoped15-second poll updates all cards, skips hidden tabs and overlapping calls, retains last counts on error; no physical cache audit. On-demand medium generation records readiness too; old medium cache hits are recognized by the background feed without re-encoding.

- Per-user Management thumbnail counts use one grouped index query on page load, current small-thumbnail signature, and zero defaults for users without images. Remaining includes pending/stale-quality/failed or deferred images. No new refresh timer or endpoint; existing unrelated resizer-status polling is unchanged. This is indexed readiness, not a physical cache audit.

## Gallery product requirements

- Opening a gallery lists immediate child folders and files.
- A user's private Gallery home is a virtual root over zero or more `UserRoots` configured in Management. Every configured root appears as a normal folder card using its editable display name and direct-child cover collage; an account with no configured roots sees an empty-state message instead of a filesystem error. Child paths use owner-scoped `@root-{id}` markers internally, but all breadcrumbs and visible names use the configured root name. Existing `ApplicationUser.RootFolder` values migrate idempotently into the first `UserRoot`, and existing folder shares, collection memberships, and legacy folder rules are prefixed with that root marker. Keep the legacy column only as a compatibility seed; new navigation and authorization must resolve through `UserRoots`.
- Management keeps each user card as an independent responsive layout. Gallery-root forms use two flexible zero-minimum field tracks inside the card and one full-width wrapping action row; at narrow widths the fields stack and actions share/wrap the available width. User card/root containers, labels, and inputs must be allowed to shrink, while long physical paths and error text wrap or clip inside the card instead of overlapping adjacent users. Keep these containment rules in the unified stylesheet.
- Gallery search and type filtering are deliberately client-side over the current rendered page. Cards expose `data-item-kind` and normalized name input; filtering toggles cards without navigation, updates `N of total shown`, keeps the Back card available, shows a designed no-results state, and does not add directory I/O. Heading counts come from `Model.Items` only. Breadcrumb construction first establishes the private/share/collection-safe path list, then collapses only middle entries when it exceeds four so an unlisted link never reveals an ancestor outside its scope.
- The sticky toolbar has two mutually exclusive states. Normal state contains Search, type filter, server sort links (or a select below 850px), saved density, and Grid/List. Selection state contains selected total, Select visible, Clear, and the existing streamed Download selected submission. Filtered-out selections remain counted, Select visible operates on visible file inputs only, and Shift selection walks visible indexes. A 520ms touch long-press with movement cancellation toggles images and other files and suppresses the synthetic follow-up click.
- Support Grid and List views; the first-use Grid default is 8 items per row, while the selected view and later Grid items-per-row remain persisted in browser local storage.
- Grid density uses a stable control and stable page width. The stylesheet root declares `scrollbar-gutter: stable` so density-driven changes in Grid height cannot make the vertical scrollbar appear/disappear and reflow the toolbar container. Gallery, Collections management, and the collection folder picker render fixed-size `−`, range, `+`, and two-character output elements. Step buttons dispatch the range's normal `input` event, preserving every existing grid update, collection-span calculation, share setting, and local-storage behavior; they disable at min/max.
- Sorting is available from the header for name, size, and modified date in ascending or descending order. Persist the last normalized sort field/direction for one year in HttpOnly, SameSite=Lax cookies scoped to the application's PathBase, and restore them whenever a private or shared Gallery URL does not explicitly supply sort parameters.
- Images use cached WebP thumbnails in the browser view. Load the original only in the full-image viewer or for download.
- Cached thumbnails return immediately. Missing thumbnails go through a singleton High/Normal dispatcher with a 256-job pending bound. The Admin-configured concurrency range is 1–16 (default 2); visible requests are High priority and active generation never starts above the current limit.
- Thumbnail `<img>` elements carry `data-thumbnail-src`. `IntersectionObserver` submits only visible images to a browser dispatcher capped at 32 simultaneous low-priority same-origin fetches so cached folder-cover tiles are not serialized in groups of four. `AbortController` cancels unfinished requests after scrolling away. Before unmodified link navigation or form submission, clear pending work and abort all active thumbnail fetches synchronously, with delayed resumption only if the current document remains active; this cancellation is what keeps navigation responsive at the higher cap. `pagehide` cancels without resumption. HTTP 503 queue-full responses retry only while the image remains visible. Browsers without IntersectionObserver use the same bounded dispatcher rather than direct unlimited image URLs.
- Because each folder card can contain four tile URLs, visible folder-cover images first perform a parallel `fetch` using `mode: same-origin` and `cache: only-if-cached`. A successful HTTP-cache response is decoded from its Blob immediately and bypasses the 32-slot dispatcher; a 504 cache miss, unsupported-mode exception, or other probe failure falls through to the normal bounded fetch. Track one probe attempt per image so a miss cannot loop. These probes must remain cache-only: server/network work continues to use the cancellable dispatcher and bounded ImageSharp queue.
- Thumbnail URLs carry `v=<algorithm-version>` plus `stamp=<UTC-modified-ticks>-<source-length>` for regular images and every direct-child folder-cover tile. Fingerprinted responses are private immutable browser-cache entries for one year; requests without a stamp require revalidation. A source content timestamp/length change or an algorithm-version bump therefore changes the URL instead of serving a stale browser entry. The existing disk-cache identity remains the final authority and includes the same source metadata plus configured thumbnail dimensions/quality.
- Deferred images stay hidden until load succeeds, then reveal with a brief opacity transition. A smooth low-contrast transform-driven shimmer and reduced-motion fallback represent loading. Terminal failures use an error mark instead of broken-image chrome.
- Non-image files remain downloadable and use an extension label instead of a thumbnail.
- Hide entries carrying Windows `Hidden` or `System` attributes (including inaccessible entries such as `System Volume Information`) across the complete file surface. Also ignore `Thumbs.db` and the common singular `Thumb.db` spelling case-insensitively: omit them from private/shared Gallery listings and folder-cover collages, reject them as collection/share roots and direct file/thumbnail/selected-download requests, and skip them in recursive streamed folder ZIPs. Attribute/enumeration failures are treated as hidden so protected metadata cannot leak or abort a ZIP.
- Users can enter child folders, download one file, or stream the current folder and all descendants as ZIP without a server-side temporary ZIP.

## Technology decisions

- Large-grid drag optimization (2026-09-09): repeated dragover used to remove/re-add the same highlight class, coupled to a continuously painting outline pulse and native card-image drag ghost. Feedback now changes only on target transitions, uses a static outline and a small dedicated text ghost. A controlled Edge fixture with2000 cards and2000 same-target events changed from3999 highlight mutations/17.8ms handler work to1 mutation/6.5ms; these are synthetic local event timings, not NAS/user-visible frame latency. Full local move/upload regression, including drag from an actual cover img, still passes.

- Folder drag correction (2026-09-09): native cover-image dragging supplied WebP as an external upload because only file cards had move handlers. Disable native card image/link drag, make owned directories draggable, clear native payload, and distinguish internal moves from OS file uploads. Move uses Directory.Move for directories with self/descendant/root/overlapping-source/active-upload rejection and unchanged ownership/antiforgery/no-overwrite checks. Folder contents retain their bytes; old share/collection paths are not automatically rewritten. Real Edge regression starts dragging directly on a decoded folder-cover image and asserts zero Upload Start requests plus successful nested image hash verification at the destination.

- 2026-09-09 writable single-root Gallery: retain UserRoot rows/markers as compatibility identities but enforce one owner row in SQLite, hide the virtual root choice and open it directly. FilesController is owner-only, antiforgery-protected, with WritePaths portable component validation and no linked paths or overwrite. UploadSessions owns serialized offset append, per-session gates and a shared mutation gate; staging files are never normal Gallery items. Completed-file publication is a destination-filesystem rename following a staged copy and root revalidation. Unique upload names and publication journals support24h cleanup; .part is never a reserved extension. File operations refresh affected direct-child index records; completed images use normal-priority small thumbnail generation. Explicit permission failures are surfaced, not silently ignored.
- file-operations.js intentionally lives outside GalleryPages page scope. It keeps a bounded two-file upload queue and batch progress across SPA routes; logout cancels pending jobs, and native unload warns before abandoning active transfers. Chunk retry checks authoritative offsets; publication retries are idempotent. Rendering is throttled and large batches reveal100 rows at a time. Drag targets include owned folders, Back, breadcrumbs and current gallery area; folder entries are recursively read including empty folders. Browser sessions do not persist file handles or resume across reload/restart. Move confirmation names source/destination and preserves completed operations on partial error. Upload/move completion invalidates the page snapshot cache.
- Existing users do not become forced-password-change accounts on migration. New users default to the flag; Management can set existing users too. Middleware gates authenticated routes and validates security stamps, while change/reset/logout remain reachable. Identity token provider lifespan is one hour; successful reset invalidates token replay. Do not expose reset tokens in logs/worklogs/screenshots. Docker mounts remain read-only by default; explicitly set WEBGALLERY_MEDIA_READ_ONLY=false and narrowly scoped host permissions to enable writes. IIS needs its specific pool identity's Modify permission on intended media roots; no blanket ACL change was made.

- Folder SPA cache (2026-09-09): bounded in-memory rendered-response snapshots provide stale-while-revalidate navigation without changing MVC/API authorization or browser URLs. Cache initial Gallery HTML before module mount and successful subsequent Gallery GETs; no session/local storage. Revalidation always runs; unchanged normalized server markup avoids DOM replacement and thumbnail flicker. Authentication/error/non-Gallery responses invalidate snapshots, and POST clears before submission. Changed listing updates preserve scroll but defer replacement during viewer/selection/focused control activity until the next visit. Unknown folders keep existing element-level skeleton behavior. Memory survives only this document, not reload/new tabs.

- Cache throughput correction (2026-09-09): medium addition still queued even cached medium behind4 network jobs, and only folder-cover small images bypassed32 network jobs; both now use cache-only probes. Uncached medium waits until small network/probes drain, while cached medium remains immediate. Upgrade dimension reads are batched per animation frame. Server cache-hit path no longer calls synchronous index ExecuteUpdate under _write before returning WebP; existing background processing records readiness after cache hits. Therefore switching quality may still inspect cached files in the index feed but viewer cache hits no longer wait for a derived SQLite write. Real user NAS throughput was not benchmarked; bounded cache-bypass scheduling has a160-item controlled regression.

- On-demand medium rendition (2026-09-09): GetOrCreateAsync medium=true uses 1500px bounds and the existing quality/source/size key. Cache lookup precedes remote availability checks. Missing medium requires connected remote; all failure paths terminate without local fallback, and Background priority is rejected. Medium requests bypass small-index RecordReady updates and do not reuse small legacy aliases. Controller uses the same private/share authorization and immutable success cache policy; missing medium returns no-store204.
- site.js keeps a separate bounded4 medium fetch queue shared by visible thumbnail upgrades and viewer preview. Offscreen/navigation abort medium network work; failed tile attempts have a 30-second eligibility delay, only revisited by normal visibility/resize events. Viewer uses a per-generation abort controller and readiness guards for small/medium/full; assign only decoded medium blobs, revoke their URLs afterward, and reject stale display completions by checking the currently assigned source. - Shared thumbnail renditions and split remote limits (2026-09-09): canonical Full/Fast versions no longer contain remote URL/mode suffixes; both backends use the same encoder quality, source fingerprint and quality. Initial remote background migration copies prior opt-in once; future remote/local changes are independent. ThumbService's server-wide cap remains a separate hard ceiling. No API-key/config rewrite occurs in Management.

## Filesystem identity and OneDrive

- IIS reads user gallery roots as its worker identity, not as the signed-in Gallery user or the Windows desktop user.
- User-profile and OneDrive roots therefore require an explicit `IIS_IUSRS` Read & Execute ACL on the selected root and descendants.
- Keep access read-only. The application writes thumbnails and SQLite state to `C:\Web\imagegallery-data`, not to the user's image root.
- ASP.NET Core Data Protection uses a persistent filesystem key ring at `Gallery:DataProtectionKeysPath` (`C:\Web\imagegallery-data\keys` in production) with application name `WebGallery`. This key directory is deployment state and must retain its files across app-pool restarts and deployments; the IIS app-pool identity needs Modify access. A first deployment of this fix invalidates cookies created with the previous ephemeral key ring once, after which the 14-day sliding authentication cookie survives normal deployments.
- Admin root-folder save checks Windows attributes and forces one enumeration under the IIS process identity. Add-folder failure distinguishes a missing path, a file supplied instead of a folder, denied/security access, invalid/unsupported path syntax, and OS I/O details. Database failures are logged and common SQLite locked/busy, read-only, disk-full, and duplicate cases are translated. The response returns to the affected user card and renders the same cause next to its Gallery folders form as well as through the global alert; it must not silently discard the submission or fall through to the generic error page.
- For OneDrive, pin gallery files locally with **Always keep on this device** before depending on unattended IIS delivery.
